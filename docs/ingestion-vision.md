# Извлечение текста и таблиц из PDF

Обычная выгрузка использует PDFium. Экспериментальный флаг `--text-engine pymupdf` меняет способ чтения встроенного текста. Для проверенных страниц, настроенных через `table_rows` и `visual_order_pages` в манифесте, сохраняется существующее извлечение PDFium.

Флаг `--ocr paddleocr` включает распознавание страниц без текста после очистки. `--ocr pp-structure` запускает PP-StructureV3 на тех же страницах и представляет таблицы отдельными строками с разделителями ячеек. Оба режима рендерят PDF через PyMuPDF и используют кириллическую модель Paddle. Выгрузки сохраняют схему страниц и идентификаторы документов.

OCR запускается на CPU. При первом запуске скачиваются веса моделей. Страницы обрабатываются локально.

## Запуск

Используйте Python 3.12. Для обычной выгрузки достаточно зависимостей проекта из группы `api`.

```sh
python -m pip install -r ml/ingestion/requirements-ocr.txt

python -m ml.ingestion.export_pages --manifest ml/ingestion/manifest.json \
  --data-dir /path/to/corpus --text-engine pymupdf --output /tmp/pages-pymupdf.jsonl

python -m ml.ingestion.export_pages --manifest ml/ingestion/manifest.json \
  --data-dir /path/to/corpus --ocr paddleocr --output /tmp/pages-ocr.jsonl

python -m ml.ingestion.export_pages --manifest ml/ingestion/manifest.json \
  --data-dir /path/to/corpus --ocr pp-structure --output /tmp/pages-structure.jsonl
```

Эти же флаги работают с `--format parsed`. Проверьте применимость новых таблиц к конкретному двигателю и условиям из заголовков. При смене извлекателя также проверьте контрольные хеши подтверждённых выдержек из `reviewed_evidence.json`.

## Смешанные страницы и структура

Флаг `--mixed-ocr` вместе с `--ocr` включает распознавание картинок на страницах, где уже есть встроенный текст.

```sh
python -m ml.ingestion.export_pages --manifest ml/ingestion/manifest.json \
  --data-dir /path/to/corpus --ocr pp-structure --mixed-ocr \
  --output /tmp/pages-mixed.jsonl
```

Области получаются из отображаемых растровых изображений PDF. Пересекающиеся изображения объединяются. Картинки меньше 36 PDF-пунктов по любой стороне пропускаются. Области с 20 и более символами встроенного текста пропускаются как уже содержащие текстовый слой. Проверенные страницы из `table_rows` и `visual_order_pages` используют прежнее извлечение.

Распознанный текст добавляется после встроенного текста страницы. Дополнительное поле `blocks` сохраняет тип, текст и координаты каждого блока. Для таблиц сохраняется `html` с `rowspan` и `colspan`, для PaddleOCR — `confidence`. Поле `extraction` содержит OCR-движок, DPI, размер отображаемой страницы и число обработанных областей.

Координаты `bbox` — PDF-пункты относительно левого верхнего угла отображаемой страницы с учётом её поворота. Поля сохраняются в `pages.jsonl` и в страницах `ParsedDocument`. Существующий загрузчик retrieval принимает эти выгрузки и индексирует их текст. HTML и координаты доступны потребителям исходной выгрузки.

Порядок между встроенным и распознанным текстом пока задаётся добавлением OCR после исходного текста. Векторные рисунки и изображения со значительным наложенным текстовым слоем требуют отдельной обработки.

На локальном пилоте созданы три смешанные страницы из вручную сверенных фрагментов РК ЯМЗ-236 и встроенного тестового заголовка. Прежний режим извлёк 0/3 растровых областей, новый — 3/3. Заголовок во всех случаях сохранился однократно.

| Режим со смешанными страницами | Text Edit ↓ на двух текстовых фрагментах | TEDS ↑ одной таблицы | TEDS-S ↑ |
|---|---:|---:|---:|
| PaddleOCR | 0,004 | — | — |
| PP-StructureV3 | 0,300 | 0,875 | 0,963 |

Это проверка маршрутизации на контролируемом PDF с реальными растровыми фрагментами. Выборка повторяет первоначальный пилот. Для оценки обобщения нужна независимая разметка естественных смешанных страниц.

## Метрики

Выберите одни и те же вручную сверенные фрагменты для четырёх режимов: PDFium, PyMuPDF, PaddleOCR и PP-StructureV3. Пример строки эталона на синтетических данных:

```json
{"id":"caption-1","document_id":"synthetic-manual","pdf_page":2,"bbox":[0.1,0.5,0.9,0.8],"text":"Рисунок 1. Схема стенда\nКрепление датчика","anchors":["Схема стенда","Крепление датчика"]}
```

`bbox` задаётся долями ширины и высоты видимой страницы с началом в левом верхнем углу. Для одной таблицы на фрагмент задайте `table_html` с эталонными `rowspan` и `colspan`. Для проверенных контрольных строк задайте `rows` как список списков обязательных фрагментов одной строки. Эталон с текстами руководств храните локально.

```sh
python -m pip install rapidfuzz Levenshtein apted lxml tqdm
python -m evaluation.ingestion --manifest ml/ingestion/manifest.json \
  --data-dir /path/to/corpus --gold /path/to/gold.jsonl \
  --engine pp-structure --omnidocbench /path/to/OmniDocBench
```

- **Text Edit Distance** — расстояние Левенштейна, делённое на длину большей строки. Меньше лучше.
- **Reading Order Edit Distance** — расстояние на последовательности найденных эталонных фраз. Пропуск фразы тоже увеличивает расстояние. Это локальная проверка порядка чтения с заранее заданными фразами.
- **TEDS и TEDS-S** — метрики из оригинального кода OmniDocBench для HTML-таблиц. Первая учитывает содержимое, вторая измеряет структуру. Выше лучше.
- **Точные строки** — доля эталонных сочетаний, для которых все фрагменты, например название и полный диапазон, найдены в одной строке.

Скрипт выводит показатели по каждому фрагменту и средние по показателям. Инициализация модели измеряется отдельно. Результат относится к локальной выборке корпуса. [OmniDocBench](https://github.com/opendatalab/OmniDocBench#end-to-end-evaluation)

## Первый замер

Два текстовых фрагмента на сканах, одна растровая таблица и две контрольные строки на обычной странице. Профиль PaddleOCR подобран на этой же выборке. Для независимой проверки нужна отдельная разметка.

| Извлекатель на контрольном фрагменте | Text Edit ↓ | Порядок чтения ↓ | TEDS ↑ | TEDS-S ↑ | Контрольные строки |
|---|---:|---:|---:|---:|---:|
| PDFium с проверенным порядком на стр. 68 | 1,000 | 1,000 | — | — | 2/2 |
| PyMuPDF `get_text(sort=True)` | 1,000 | 1,000 | — | — | 0/2 |
| PaddleOCR, кириллица, 250 DPI | 0,004 | 0,125 | — | — | 0/2 |
| PP-StructureV3, кириллица, 250 DPI | 0,296 | 0,750 | 0,875 | 0,963 | 2/2 |

Прочерк означает, что на этом фрагменте извлекатель не создал HTML-таблицу. TEDS рассчитан оригинальным кодом OmniDocBench на коммите `baf13e5`.

Ближайшее улучшение — разметить ещё несколько растровых и смешанных страниц. Для текста сравнить PaddleOCR с текущим извлечением, для таблиц проверить PP-StructureV3 по ячейкам, диапазонам, единицам и применимости колонок. Разбор порядка на самих схемах проверять отдельно от OCR их подписей.

## Сравнение настроек OCR

Сравнены 16 профилей на трёх фрагментах разработки. Два новых фрагмента тех же страниц зарезервированы для проверки выбранных настроек. Это небольшой локальный набор, в нём нет независимых документов.

Изменялись DPI, перевод изображения в оттенки серого, классификация поворота строки, модель детекции PP-OCRv4 вместо PP-OCRv5, размер изображения для детектора, способ построения HTML таблицы и выбор обработчика по наличию таблицы.

| Линованная таблица | Обычная сборка HTML | Сборка по ячейкам |
|---|---:|---:|
| TEDS, фрагмент разработки | 0,875 | 0,912 |
| TEDS-S, фрагмент разработки | 0,963 | 1,000 |
| TEDS, новый контрольный фрагмент | 0,917 | 0,980 |
| TEDS-S, новый контрольный фрагмент | 0,938 | 1,000 |

Выбранный режим доступен через `--ocr pp-structure --table-html cells`. Он использует распознанные ячейки линованной таблицы при построении HTML. Обычный режим `--table-html model` остаётся значением по умолчанию.

Увеличение DPI до 300 и 400 и оттенки серого не улучшили текст PaddleOCR на фрагментах разработки. Альтернативный детектор и классификация поворота строки дали больше ошибок. На контрольном абзаце PaddleOCR дал Text Edit 0,253, а PP-StructureV3 — 0,148. Автоматическое правило «всё вне таблиц в PaddleOCR» пока не подходит для общего включения.

Отчёты по каждому профилю хранятся в `evaluation/results/ingestion-ablation-dev-20261127.json` и `evaluation/results/ingestion-ablation-validation-20261127.json`. Время измерено по одному проходу без инициализации моделей. Малой выборки недостаточно для вывода о скорости на корпусе.

```sh
python -m evaluation.ingestion_ablation --manifest ml/ingestion/manifest.json \
  --data-dir /path/to/corpus --gold /path/to/local-gold.jsonl \
  --omnidocbench /path/to/OmniDocBench \
  --configs evaluation/results/ingestion-ablation-dev-20261127.json \
  --output /tmp/ingestion-ablation.json
```

## Белые поля перед OCR

Флаг `--ocr paddleocr --ocr-padding 64` добавляет белую рамку шириной 64 пикселя вокруг изображения до распознавания. Координаты результатов пересчитываются обратно на исходную PDF-страницу, а ширина рамки записывается в `extraction.padding_pixels`. По умолчанию рамка не добавляется.

В сравнении семи вариантов подготовки изображения белые поля помогли тексту, обрезанному близко к границам фрагмента. Средний Text Edit по трём фрагментам снизился с 0,08682 до 0,00258. На сложном абзаце он снизился с 0,25271 до 0. Рамка 24 пикселя дала меньший прирост. CLAHE, повышение резкости, порог Оцу и адаптивная бинаризация на этой выборке не изменили результат.

Один дополнительный фрагмент, исключённый из подбора, распознан без ошибок и с рамкой, и без неё. Это проверка на фрагментах тех же страниц, независимых документов в выборке нет. Результат не является оценкой ошибки на всём корпусе. Фрагмент, ранее использовавшийся для проверки маршрутизации, в этом эксперименте включён в набор подбора.

Отчёты находятся в `evaluation/results/ingestion-preprocess-tuning-20261127.json` и `evaluation/results/ingestion-preprocess-validation-20261127.json`. Режимы подготовки изображения воспроизводятся через `evaluation.ingestion_ablation`.
